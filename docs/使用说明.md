# 本地 CI 使用说明

日常流程：`git push` → App 自动跑测试 → 构建并推送镜像 → 替换 k8s 上的服务镜像。需要确认的分支停在「等待确认」，点一下再替换。

## 1. 准备

- macOS 27，Git 2.54 或更高（推送监听使用 Git 的配置式钩子）。
- 终端里能直接用的 `docker` 和 Buildx（已经 `docker login` 过目标镜像仓库）和 `kubectl`。App 读取登录 shell 的环境，终端里能找到的命令，App 里也能找到。
- 构建：`scripts/build.sh`（加 `--skip-tests` 跳过包测试），产物在 `build/DerivedData/Build/Products/Debug/LocalCICD.app`。本机安装包：`scripts/release.sh --local`，产物在 `build/releases/` 下。

## 2. 导入 k8s 连接

打开「设置 → k8s 连接」，点「导入」：

1. 选择 kubeconfig 文件，选一个 context。页面显示集群地址、namespace 和客户端证书到期日。
2. 起一个名字，例如「测试环境」「正式环境」。配置文件里用这个名字引用。
3. 导入后 kubeconfig 存在钥匙串里，数据库只记名字和展示信息。原文件之后可以删除或修改，不影响 App。

导入不会访问集群，也不会执行 `exec` 认证插件（只保留配置并提示）。连接可以重命名、替换文件、删除；删除被项目引用的连接前会列出引用它的项目。

## 3. 写 `.local.cicd.yml`

放在仓库根目录，提交后生效。新版统一使用镜像列表与部署批次；不接受旧的 `build.image` / `deploy[].branch` 格式，不自动修改项目配置。

单镜像也使用相同列表结构：

```yaml
test:
  - go vet ./...
  - go test ./...
build:
  images:
    - name: app
      image: registry.example.invalid/cicddemo/cicddemo_go:${TIME}
      dockerfile: Dockerfile
deploy:
  - name: 测试发布
    branches: [dev, main]
    k8s: 测试环境
    targets:
      - {build: app, namespace: demo, deployment: cicddemo, container: cicddemo}
  - name: 正式发布
    branches: [main]
    k8s: 正式环境
    confirm: true
    targets:
      - {build: app, namespace: demo, deployment: cicddemo, container: cicddemo}
```

多镜像示例（地址和目标需按项目实际填写）：

```yaml
build:
  parallel: 2
  images:
    - name: api
      image: registry.example.invalid/demo/api:${BRANCH}-${SHA}
      command: make push-api IMAGE_TAG=${BRANCH}-${SHA}
    - name: worker
      image: registry.example.invalid/demo/worker:${BRANCH}-${SHA}
      command: make push-worker IMAGE_TAG=${BRANCH}-${SHA}
deploy:
  - name: 测试发布
    branches: [main]
    k8s: 测试环境
    parallel: 2
    targets:
      - {build: api, namespace: demo, deployment: api, container: api}
      - {build: worker, namespace: demo, deployment: worker, container: worker}
  - name: 正式发布
    branches: [main]
    k8s: 正式环境
    parallel: 2
    confirm: true
    targets:
      - {build: api, namespace: demo, deployment: api, container: api}
      - {build: worker, namespace: demo, deployment: worker, container: worker}
```

| 字段 | 说明 |
| --- | --- |
| `test` | 可省略或 `[]`，必须是命令列表；顺序执行一次 |
| `build.parallel` | 默认 1，范围 1–50，构建推送与摘要核验共用这个并发上限 |
| `build.images` | 1–50 个镜像；`name` 唯一，以字母开头，最多 64 位，只含字母、数字、`_`、`-` |
| `images[].image` | 完整镜像地址，可用 `${TIME}`、`${SHA}`、`${BRANCH}` |
| `images[].dockerfile` | 项目内文件，构建上下文为项目根目录；App 执行 docker build + push |
| `images[].platform` | 可省略，只与 Dockerfile 一起用，如 `linux/amd64` |
| `images[].command` | 与 Dockerfile 二选一，命令必须构建并推送声明的镜像 |
| `deploy[].name` | 唯一批次名，最多 64 字符 |
| `deploy[].branches` | 必填非空列表，精确匹配分支；未匹配时不运行 |
| `deploy[].k8s` | 必填连接名，不回退到默认集群 |
| `deploy[].parallel` | 默认 1，范围 1–50；单批目标从替换到健康观察都占用并发名额 |
| `deploy[].confirm` | 默认 false；true 时确认整个批次；自身镜像就绪后可任选批次确认 |
| `deploy[].targets` | 必填非空列表；所有批次总计最多 50 个目标 |
| `targets[].build` | 必须引用构建项的 name，不自动猜测 |
| `namespace` / `deployment` / `container` | 每个目标明确指定替换位置 |

变量在运行创建时固定：`${TIME}` 为北京时间 `yyyyMMdd.HHmmss`，`${SHA}` 为提交前 12 位，`${BRANCH}` 将 `[A-Za-z0-9_.-]` 之外字符换成 `-`。其他 shell 变量仅在 command 中由 shell 解释，不在镜像地址里求值。

命令环境含 `CICD_TIME`、`CICD_SHA`、`CICD_BRANCH`；每个构建另有自身的 `CICD_BUILD`、`CICD_IMAGE`。公共测试不提供当前构建/镜像变量，终端残留的同名变量也会清除。

### 执行、失败与镜像核验

1. 筛选命中分支的批次，只构建它们引用的镜像，每项一次。
2. 执行前校验 Dockerfile、连接和工作区 HEAD；公共测试失败则不构建。
3. 有界并行构建。命令成功后通过 `docker buildx imagetools inspect` 查询仓库清单，记录 SHA-256 digest；查询失败、超时或无有效摘要时，依赖该镜像的批次不部署；其他服务继续。需要本机 Docker Buildx 和读取清单的权限，认证沿用本机 Docker 配置。
4. 每批只等待它引用的镜像核验成功，随后自动部署或开放确认。其他镜像仍在构建、其他批次仍在等待或部署，都不会挡住它。每个目标使用冻结的 `仓库@sha256:...`，同一批按 parallel 限流并完成健康观察。
5. 构建失败只跳过引用它的批次，其他服务继续。一个部署目标失败时，该批未开始的目标跳过，已开始目标收尾，其他批次仍可运行。仍有执行或等待确认时不会提前结束整个运行，全部处理完后汇总失败。已成功替换的目标保留，不自动回滚；用户取消会终止全部构建和部署进程组。

命令模式必须保证推送的是本次构建产物；清单核验确认镜像存在并冻结其摘要，不通过日志猜测镜像，也不能证明任意自定义脚本的源码来源。重新运行可能覆盖相同标签，旧运行重新替换仍使用旧 digest；仓库删除旧 digest 后恢复会失败。

同一分支重复指向同一连接、namespace、Deployment、容器会报错。同一批内替换同一 Deployment 的多个容器时，必须设 parallel: 1；跨批次指向同一 Deployment 时也会自动排队，避免互相触发新 rollout。不同 Deployment 没有先后顺序。

并行命令共享项目工作目录，构建脚本需要支持同时执行；默认 parallel 为 1。

需要分别控制两个服务时，拆成两个 `confirm: true` 批次，各自镜像就绪即可点击。批次在文件里的顺序只控制显示，不表达发布依赖；需要先观察测试环境再发布正式环境时，由操作者选择确认顺序。一个批次包含多个镜像时，仍需等该批引用的全部镜像就绪后整批确认。App 的 Pod 健康检查不包含 Kafka 消费组、错误 Topic 或业务接口验收。

替换执行的是：

```bash
kubectl set image deployment/<deployment> <container>=<image> -n <namespace>
kubectl rollout status deployment/<deployment> -n <namespace> --timeout=10m
```

「替换完成」不只是镜像换上去了，还要确认服务真的启动。App 的判断分三步，查询全部只读（`kubectl get deployment / pods / events`、`kubectl logs`），不改集群：

1. **读 deployment**：取 matchLabels 找新 Pod，并看目标容器有没有配置就绪探针（readinessProbe）。没有时日志里会提醒：这种服务进程一启动 Kubernetes 就认为可用，rollout 完成不代表服务起来了，App 只能确认进程在观察期内没有退出。建议给服务加上就绪探针。
2. **等 rollout 时每 2 秒查一次新 Pod**，状态有变化就在日志里写一行，例如 `Pod live-xxx：Running，容器 live 等待中（CrashLoopBackOff），重启 3 次`。出现不会自己恢复的状态（`CrashLoopBackOff`、`ImagePullBackOff`、`CreateContainerConfigError` 等，或反复非零退出）时，不等 10 分钟超时，立即停止等待并判为失败。rollout 自己失败或超时时，补查一次：起不来的说明原因，一直没有就绪的说明「未就绪」。
3. **rollout 完成后再观察 60 秒**：rollout 完成时就在的新 Pod 在这段时间里重启或进入失败状态，判为失败；观察结束时还要求它们仍然就绪。以 rollout 完成时的重启次数为基准，重新替换同一镜像时以前的重启不算。

失败时日志里依次写出：哪个 Pod、哪个容器、原因、重启次数和上次退出码；这个 Pod 最近的告警事件（例如探针失败、拉取镜像失败、调度失败）；容器崩溃过时附上**上一次运行**的最后 200 行日志（`kubectl logs --previous`），没有重启过但已在运行的附上当前日志。拉不到镜像、建不了容器时没有日志。

界面上：阶段日志上方显示结论，运行标题下显示开头两行。失败时是「Pod 哪个容器怎么失败的」加最能说明问题的一行——崩溃过的取日志里的报错（例如 `Error: Load(missing configuration field "teacher_annotations")`），没运行起来的取告警事件（例如 `Unhealthy：Readiness probe failed: … connection refused`）；「Back-off restarting failed container」这类只重复状态的说明不当作原因。成功时是「替换完成：N 个新 Pod 已就绪，60 秒内没有重启」，没有就绪探针时附带提醒。

连续 3 次读不到 Pod 状态（例如权限不够）会报告健康检查未完成，不能降级为成功。失败时 deployment 已经指向新镜像，App 不会自动回滚：修好后重新推送；要先恢复服务，可以在之前成功的运行上点「重新替换」。

kubeconfig 通过临时文件（权限 0600，用完删除）和 `KUBECONFIG` 环境变量传给 kubectl，不出现在命令参数和日志里。

写错时（未知字段、`dockerfile` 和 `command` 同时写、`dockerfile` 指向项目外、YAML 格式错误等），运行不会执行任何命令，界面直接显示原因和行号。项目概览里也会实时显示当前提交的配置是否有效。

## 4. 添加项目并开启推送监听

1. 侧栏点「添加项目」，选择仓库目录。添加不会运行任何命令。
2. 项目概览显示配置检查结果和替换目标表（分支 → 环境 / namespace / deployment，自动或需确认）。名称默认是仓库文件夹名，可点「重命名…」修改，留空恢复文件夹名。
3. 打开「推送监听」，确认面板里可以展开「将执行的命令」，查看要写入仓库本地 Git 配置的钩子命令。原有钩子照常执行；关闭监听会完全撤销。

之后在终端里正常 `git push`。推送成功、且分支在 `deploy` 里时，App 创建一次运行；推送失败、删除分支、推送标签都不会运行。

注意：

- App 读取的是**推送的那个提交**里的 `.local.cicd.yml`，但命令在你的工作区里执行。工作区 HEAD 不是推送的提交时（例如推送了别的分支），运行不执行任何命令并说明原因；工作区有未提交改动时，日志开头会警告，照常执行。
- `git push --no-verify` 等跳过钩子的推送无法被监听。
- App 关着时的推送会在下次打开时补处理；关闭窗口后 App 仍在后台监听。

## 5. 查看运行和确认替换

- 中栏是运行列表（分支、短提交、提交说明首行、镜像标签、状态）。由重新运行或重新替换产生的运行带 ↩ 标记。右栏是运行详情：公共测试、每个镜像的构建推送、每个替换目标各一个阶段，点阶段查看日志。日志自动换行，可全选复制。
- 顶部显示当前选中的构建或部署目标的标签地址，「复制镜像地址」复制同一地址；核验完成后也保留标签，悬停可查看完整冻结 digest。公共测试阶段显示本次镜像汇总。部署确认和实际替换继续使用完整 digest 锁定镜像。
- 某批次进入「等待确认」时，点击对应阶段，原日志区域显示该批的环境、并发上限、全部目标和冻结镜像；即使运行总体仍显示「运行中」也可以确认。点「确认批次」后再核对一次；一次确认执行该批次全部目标。点「跳过批次」只跳过该批全部成员，不影响其他批次。
- 新版运行的等待确认持久保留，不因后续运行过期；App 重启前已点击但尚未执行的确认，需要重新确认。
- 回滚：点「重新替换」，沿用原运行整组 digest 和批次，不测试、不构建、不检查工作区 HEAD。所有所需镜像都成功构建并核验后才可使用；确认批次仍需确认。
- 旧格式运行记录保留可查看，不执行旧计划的确认或重新替换；请提交新版配置后创建新运行。旧配置不会自动迁移。
- 「重新运行」按原提交重新读配置、重新测试和构建，要求工作区 HEAD 就是那个提交。
- 「删除运行」删除运行记录和日志，不影响已推送的镜像和集群；正在执行或排队的运行要先取消。
- 「取消运行」会终止正在执行的命令；已经发出的替换不会回滚。
- 同一项目一次只跑一个运行，新的推送排队。退出 App 时正在执行的运行在下次打开时显示「已中断」，可以「重新运行」，不会自动重跑。
- 「设置 → 通用」可以开启系统通知（只在等待确认和失败时通知）和登录时打开。

### 菜单栏快捷操作

屏幕顶部菜单栏的「本地 CI」图标提供系统原生菜单，跟随 macOS 27 的浅色和深色外观。关闭主窗口后仍可打开菜单、查看状态，推送监听继续运行；「退出本地 CI」才会退出应用，存在执行任务时仍会提示确认。

- 菜单显示运行中、排队和等待确认的运行数量。一个运行仍在构建其他镜像时，其就绪批次的等待确认也会计入；「最新失败」只统计各项目最新运行的失败，不累计旧失败。
- 展开项目可打开概览或选择运行。每个项目最多展示 8 条，优先显示执行、排队和等待确认的运行，完整历史在主窗口查看。
- 展开运行可查看日志、复制镜像标签地址、取消或重新运行。「查看并确认替换…」会打开已有确认面板，核对环境与目标后再确认，不会直接部署。
- 菜单底部可打开设置或退出。菜单栏图标依次优先提示执行中、等待确认、最新失败和排队状态。

## 6. 数据与凭据

- 数据在 `~/Library/Application Support/<bundle id>/`（「设置 → 通用 → 数据目录」可在访达中显示），包括数据库 `localcicd.sqlite` 和各阶段日志。
- kubeconfig 只在钥匙串里。日志对已登记的敏感值脱敏。
- docker 的登录信息由本机 docker 和它的凭据助手管理，App 不读取也不保存镜像仓库密码。
