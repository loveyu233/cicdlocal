# 本地 CI 设计

产品定义和约束见 [agents.md](../agents.md)，这里只说明实现。

## 1. 包划分

依赖从下到上，界面只依赖 ApplicationKit 和 Models。

| 包 | 职责 | 依赖 |
| --- | --- | --- |
| Models | ID、项目、推送事件、引用更新、运行、阶段、k8s 连接等值类型和状态枚举 | 无 |
| Platform | 子进程与进程组（swift-subprocess）、钥匙串、单实例锁、`AppPaths` 目录布局 | swift-subprocess |
| LogKit | 跨块 UTF-8/ANSI 处理、敏感值脱敏、阶段日志分段落盘与上限截断 | Models |
| GitKit | git 命令封装：解析提交、读取提交里的文件、HEAD、钩子配置、`ls-remote` 核对 | Platform、Models |
| Storage | GRDB 数据库、迁移、仓储、观察 | Models、GRDB |
| PushWatch | 钩子安装与卸载、spool、推送确认；`HookProtocol` 供钩子程序使用 | Models、GitKit、Storage、Platform |
| Runner | `.local.cicd.yml` 解析与校验、变量、登录 shell 环境、阶段执行、kubectl 替换 | Platform、LogKit、Yams |
| ApplicationKit | 编排：项目（含重命名）、推送分发、运行队列、确认 / 跳过 / 取消 / 重新运行 / 重新替换 / 删除运行、k8s 连接导入 | 以上全部 |

`HookHelper/` 是 App 内嵌的钩子程序，只调用 `HookRuntime.run()`。

## 2. 数据流

```
git push（终端）
  └─ pre-push 钩子 ──────────── 写推送意图 intent.json 到 spool
  └─ reference-transaction 钩子 ─ 写远端跟踪引用已更新的回执 receipt.json
        │
App：SpoolWatcher 发现新文件 → PushConfirmation.scan
  ├─ 有本次推送进程的回执 → 确认（reference_transaction）
  ├─ 推送进程成功退出但没有回执 → git ls-remote 核对（ls_remote）
  └─ 推送进程已结束仍无证据 → 无法确认，不运行
        │
PushService.dispatch（每个引用更新只处理一次，结果写入 push_dispatch）
  └─ RunExecutor.prepare
       读 `git show <sha>:.local.cicd.yml` → 校验格式、分支、k8s 连接名、工作区 HEAD
       ├─ 分支不在配置里 / 没有配置文件 → 不创建运行，只记处理结果
       ├─ 校验失败 → 创建一个直接失败、没有阶段的运行，界面显示原因
       └─ 通过 → 创建排队的运行，阶段：测试、构建推送、每个替换目标一个
        │
RunExecutor 项目队列（同一项目一次一个）
  公共测试 → 有界并发构建/核验 digest
  └─ 每个部署批次仅依赖自身镜像，就绪后独立执行（批内有界并发）
  └─ confirm: true 的整批目标进入「等待确认」，运行活跃时确认由当前调度器接收，空闲时排回项目队列；不等待前批
```

- 运行开始时用 `ShellEnvironment.capture()` 取一次登录 shell 环境；每条命令 `$SHELL -c <命令>` 在项目目录执行，stdin 为空。
- 运行计划（展开后的命令、镜像、目标）以 JSON 存在 `run.plan_json`，新版确认替换和重启后都按这份计划执行，不重新读配置；「重新运行」会按原提交重新读配置，`${TIME}` 取新时间。
- 新版计划的旧等待确认不过期，有更新的运行后仍可确认（2026-10-23 用户决定，用于回滚）。`StageStatus.expired` 只用于显示早期版本留下的记录。
- 「重新替换」（`redeploy`）：复制原运行的提交、提交说明、镜像和计划，`rerun_of` 指向原运行；测试、构建推送阶段直接记为跳过，替换阶段按原计划执行或等待确认。执行时只有替换阶段待执行，所以不检查工作区 HEAD。条件见 `RunExecutor.canRedeploy`：有镜像和计划、已结束或等待确认、全部所需构建成功且摘要齐全（或本身就是重新替换）。
- 删除运行：只允许已结束或等待确认、且不在执行或确认队列里的运行；删除数据库记录（阶段级联，推送记录和 `rerun_of` 置空）和 `logs/runs/<id>`。
- 提交说明在创建运行时用 `git log -1 --format=%B` 读取并存入 `run.commit_message`（迁移 v2，最多 2000 字符）；读取失败不影响运行。
- App 退出时终止正在执行的进程组；下次启动把「运行中」改为「已中断」，等待确认保留，排队继续。

## 3. 数据库

文件：`~/Library/Application Support/<bundle id>/localcicd.sqlite`，WAL，外键开启。迁移只追加，当前为 `v2`。旧版本的 `state.sqlite` 原样保留，不读取也不删除。

| 表 | 内容 |
| --- | --- |
| `project` | 名称、仓库路径（唯一）、钩子模式 |
| `push_event` | 一次推送：spool 事件 ID（唯一，用于去重）、远端名和地址 |
| `ref_update` | 推送中的一个引用：旧 / 新提交、确认状态和来源 |
| `push_dispatch` | 每个引用更新的处理结果：创建的运行或不运行的原因 |
| `run` | 分支、提交、镜像、运行计划、状态、时间；`ref_update_id` 唯一，一个引用更新最多一次运行 |
| `run_stage` | 序号、种类（test / build / deploy）、替换目标键、状态、时间 |
| `k8s_connection` | 连接名（唯一）、钥匙串 account、展示信息（集群地址、namespace、证书到期日）；没有存放 kubeconfig 的列 |

阶段日志在 `logs/<运行>/<阶段序号>`，不进数据库。

## 4. 凭据与安全

- kubeconfig 导入时只保留所选 context 及其引用的 cluster / user，整份存入钥匙串；`exec` 认证插件不执行，只保留配置并提示。
- 替换的判定见 agents.md §5。`KubeDeployer` 绑定 Deployment UID 和完整 Pod 模板；`PodInspector.snapshot` 按 Deployment → ReplicaSet → Pod 的 controller ownerReferences、模板和镜像确认所属关系，`DeploymentSnapshot` 校验 observedGeneration、更新/可用副本和所有目标 Pod 的 Ready/运行状态。`KubeJSON` 保留模板 spec 全部字段，防止只比较镜像漏掉命令或环境变量变更；ReplicaSet 注入的 pod-template-hash 不参与模板比较。
- 任务组并行等待 rollout 和健康检查；失败或取消时终止另一任务的进程组。每 2 秒检查状态，`StatusLog` 去重、记录恢复，并在 ErrImagePull / ImagePullBackOff 的 30 秒恢复窗口内立即展示原始事件。明确的崩溃、异常终止、OOM、初始化或配置故障及时失败。连续 3 次读取错误报告健康检查未完成，不降级成功。
- rollout 完成后要求全部目标副本连续就绪 60 秒，默认总观察上限 180 秒。基线按 Pod UID/容器名保存，新增重启失败；Pod 替换、扩缩容、未就绪和查询中断重置稳定窗口。零副本和没有目标 Pod 不能成功。未配置 readinessProbe 时，结果明确说明业务可用性未验证。
- `report` 在 90 秒总上限内采集最多 3 个异常 Pod、每 Pod 最多 3 个异常容器的证据：按 Pod UID 查询 Warning 事件，分别读取当前日志和重启前日志（每份 200 行/64 KiB，命令超时 10 秒）。长事件保留至 8 KiB，摘要保留首尾，避免丢掉长镜像地址末尾的认证错误；原始失败原因不被诊断读取失败覆盖。没有 Pod 时补查 Deployment 和 ReplicaSet 告警。`RunExecutor` 沿用日志及阶段/运行 message 的脱敏和持久化，复用原有显示区域；App UI 不变。查询只读，不自动回滚。
- 替换时从钥匙串取出，写到运行临时目录下 0600 的文件，以 `KUBECONFIG` 环境变量传给 kubectl，结束后删除；kubeconfig 不出现在命令参数、数据库和日志里。
- 导入的 kubeconfig 中的 token、私钥等登记为敏感值，日志落盘前脱敏，跨块输出也不会漏出。
- docker 使用本机 PATH 里的 `docker` 和本机已有的登录，App 不读取、不保存镜像仓库密码。
- 配置文件本身是符号链接、`dockerfile` 解析后位于项目外，都按配置错误处理。
- spool 和数据目录权限 0700；spool 文件经临时文件原子 rename 发布，读取不跟随符号链接并限长。
- 外部进程一律用参数数组启动；只有配置里写的命令交给 shell。

## 5. 界面

- `App/Main`：三栏 `NavigationSplitView`——项目侧栏、运行列表、运行详情（阶段、日志、复制镜像地址、取消 / 重新运行 / 确认替换 / 跳过）。日志用 `NativeLogText`（AppKit 文本视图，自动换行、可整段选中）。
- `App/Project`：项目概览——配置检查结果、替换目标表、推送监听开关。
- `App/Settings`：「k8s 连接」和「通用」两页。
- `App/Shared`：`AppModel`（观察数据库并转发操作给 ApplicationKit）、系统通知、状态颜色与图标。


## 6. 多镜像与批次执行（2026-10-24）

- `LocalConfig` 只解析新版列表语法；`RunPlan.version = 2` 保存 images、parallel、batches 和每个镜像的 digest。旧 JSON 不隐式升级，不删除历史数据。
- 阶段序号只用于排序与日志目录。`target_key` 保存构建键或含批次名的目标键；禁止按 `ordinal - 2` 推导目标。
- `IndependentScheduler` 以结构化任务组同时调度构建与部署批次，构建限流按计划 parallel；仅在活跃任务期间每 100ms 检查已持久化的确认，空闲时退出并释放项目队列。不同批次独立运行，相同工作负载按连接、namespace、Deployment 互斥。批内仍由 `ConcurrentStages` 限流并在失败后停止启动该批新目标；取消传播至全部子任务和外部进程组。
- `BatchRepository.transformPlan` 在单次写事务内合并每个构建的 digest，避免并发完成覆盖。`waitForBatch` 同时将所有成员置为等待；`changeWaitingBatch` 以运行归属、自身镜像构建完成和全体未确认作为条件原子确认/跳过，应用层另核对冻结摘要。
- 有执行任务时保持运行中，即使有其他失败或等待项；空闲且有等待确认时保持 waiting，全部结束后才汇总失败。跳过空闲运行时持久改为 queued；活跃运行由原调度器继续。未执行的确认重启后重新要求确认，恢复时开放旧版串行调度遗留但自身镜像已就绪的手动批次，不因此自动发起替换。
- `RunDetailView` 每次收到运行更新重新解码计划，显示所选目标实际镜像。确认面板和对话框列出整批目标；沿用现有 Grid、阶段按钮、三栏布局和日志样式。
- digest 查询使用 Docker 官方的 [imagetools inspect](https://docs.docker.com/reference/cli/docker/buildx/imagetools/inspect/) 清单 JSON，60 秒超时、64 KiB 捕获上限；认证由本机 Docker 管理。
